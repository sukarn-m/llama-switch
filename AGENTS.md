# AGENTS.md

> **⚠ Project-specific configuration.** The runtime `config/config.yaml` (gitignored) contains machine-specific paths, GPU topology, and bind addresses. Do not assume any example values — always review `config/config.yaml` for your own deployment.

Guidance for AI coding agents working in the `llama-switch` codebase.

## What this project is

`llama-switch` is a **GPU model multiplexer for `llama-server`** (from llama.cpp). It is an HTTP reverse proxy that presents a single OpenAI-compatible endpoint and transparently loads/unloads different GGUF models on one or more GPUs behind the scenes. It was written to replace a shell script (`llama-server.sh`) that ran a single fixed model — now many models can coexist and be switched on demand within VRAM and concurrency limits.

Key idea: a client sends `POST /v1/chat/completions` with `{"model": "my-model", ...}`. The proxy parses the `model` field, ensures that model's `llama-server` backend is running (spawning it if needed, evicting least-recently-used models to make room), and forwards the request — including SSE streaming — to that backend on a dynamically-allocated loopback port.

It is a **single-binary Go program** with no subpackages and one third-party dependency (`gopkg.in/yaml.v3`). Target environment is NVIDIA CUDA multi-GPU Linux (it shells out to `nvidia-smi` for VRAM accounting).

## Architecture & request flow

```
Client ──HTTP──▶ ProxyServer (:8080)
                   │
                   ├─ GET  /                → health
                   ├─ GET  /v1/models       → OpenAI model list (status, context_length, input_modalities)
                   ├─ GET  /models          → llama.cpp router model list (with status)
                   ├─ POST /models/load     → explicitly load a model {"model":"id"}
                   ├─ POST /models/unload   → explicitly unload {"model":"id"} (Open WebUI "Eject")
                   ├─ GET  /v1/loaded       → legacy: list loaded models only
                   ├─ POST /admin/profile   → profile VRAM via running service (SSE stream)
                   └─ everything else       → handleProxy
                                            │
                    parse "model" from JSON body
                                            ▼
                   BackendManager.EnsureLoaded(modelID)
                     ├─ already loaded? → reuse
                     ├─ else: ensureCapacityLocked
                     │    ├─ enforce MaxModels (evict LRU)
                     │    └─ enforce per-GPU VRAM + 1GB headroom on GPU0 (evict LRU)
                     ├─ startBackendLocked: alloc port, spawn backend,
                     │    wait for health 200 (HealthTimeoutSeconds)
                     └─ return *Backend
                                            ▼
                   NewModelHandler(modelID) registered?
                     ├─ yes → forwardWithHandler: force non-streaming,
                     │        fetch response, ProcessResponse(), return JSON
                     └─ no  → forward(): proxy to 127.0.0.1:<port>,
                              stream response back if "stream":true
```

- Each loaded model = one `llama-server` (or custom binary) child process on its own port from `backend_port_start`–`backend_port_end`.
- Backends are addressed only on loopback (`127.0.0.1`); the public listener binds to the configured `host` (set in `config.yaml`).
- The idle sweeper goroutine (`idleSweeper`) unloads any backend untouched for `idle_timeout_minutes`, polled every `sweep_interval_seconds`.

## Per-model runtime override

Models can use a different binary than `backend.binary`, with their own arguments, environment, and health endpoint. This allows running non-llama-server backends (e.g. vLLM, Python servers) alongside regular GGUF models. Set these optional fields in a model's config:

| Field | Purpose | Default |
|-------|---------|---------|
| `binary` | Per-model binary path (overrides `backend.binary`) | `backend.binary` |
| `args` | Raw args list with `{port}` placeholder, bypasses llama-server flag construction | `BuildArgs()` output |
| `health_path` | Custom health check endpoint | `/health` |
| `env` | Per-model env vars, merged on top of `backend.env` | `backend.env` only |

When `args` is set, `BuildArgs()` uses the raw list directly (with `{port}` replaced by the dynamically assigned port) — no `-m`/`--mmproj`/`-c` flags are generated. When `binary` is set, it's resolved via PATH lookup. The rest of llama-switch (VRAM management, LRU eviction, idle sweeping, proxy forwarding) works unchanged because it's all process-and-HTTP-based.

## Model handlers

A model handler is a Go type implementing the `ModelHandler` interface (`MatchesModel`, `ProcessResponse`). When a request targets a model with a registered handler, `handleProxy` routes through `forwardWithHandler` instead of `forward`: the response is read in full, post-processed by the handler, and returned as a single JSON response. Streaming requests are forced to non-streaming (the handler needs the complete output).

Handlers are registered in `NewModelHandler()` in `src/chandra_handler.go`. To add a new handler: implement the interface in a new file under `src/`, add a registration line. To remove a handler: delete its file and the registration line. The generic infrastructure (`ModelHandler` interface, `forwardWithHandler`, `forceNonStream`) stays in `src/proxy.go` and can be reused by future handlers.

### Chandra 2 OCR handler

The Chandra handler (`src/chandra_handler.go`) post-processes responses from the Chandra 2 OCR model (a Qwen3.5-based VLM):

1. **Extracts HTML from the correct field** — checks `content` first, falls back to `reasoning_content` (Qwen3.5 thinking mode sometimes routes output there)
2. **Strips chain-of-thought** — removes any thinking text before the first `<div>` tag
3. **Converts structured HTML to markdown** — Chandra outputs `<div data-bbox="..." data-label="...">` blocks; the handler converts tables, lists, bold, underline, headers, and image descriptions to clean markdown
4. **Fixes Devanagari conjunct errors** — Chandra drops the `र` in certain conjuncts (कय→क्रय, केता→क्रेता, विकय→विक्रय, केती→क्रेती)
5. **Strips page headers/footers** — blocks with `data-label="Page-Header"` or `"Page-Footer"` are omitted

## Prompt-progress keepalive

llama-server sends nothing on a streamed request while it processes the prompt, apart from a bare `:` SSE comment every 30 s (the first one 30 s in). On a slow model a long prompt takes minutes: `qwen-27b` and `davidau-27b` process about 185-215 tokens/s, so a 29k-token prompt is silent for about 150 s. A client that waits a fixed time for the first `data:` event gives up first. On 2026-11-18 sai-portal's 60 s first-event gate cut `davidau-27b` and then `qwen-27b` on the same 29k-token prompt, logged both as "stream wedge", and failed over to the next model each time; every failover made llama-switch evict the model it was just running.

`src/promptprogress.go` fixes this in the proxy. For a streamed request on `/v1/chat/completions` or `/chat/completions` whose body does not set `return_progress`, `forward()` adds `"return_progress": true`. llama-server then sends a progress-only chunk (`delta` `{"role":"assistant","content":null}` plus a `prompt_progress` member) immediately and after each prompt batch. `streamSSE` rewrites them: the first becomes an ordinary opening chunk without `prompt_progress` (so clients see a standard data event within about a second), later ones become `: prompt progress processed=P total=T cache=C` comments (llama-server's raw values), and everything from the first token on passes through unchanged.

- A client that sets `return_progress` itself gets llama-server's chunks untouched.
- Models with raw `args` are skipped (they may not be llama-server). `server.stream_prompt_progress: false` turns the feature off.
- Trade-off: once the opening chunk is out, a client can no longer treat the backend as silent, so a backend that hangs mid-prompt is caught only by the client's overall timeout, not by a first-event gate.
- Non-streamed requests are unchanged: headers still arrive only when the response is complete.

## Engine: the llama-server binary

The backends run **Unsloth Studio's prebuilt llama.cpp**, not a locally built
one: `~/.unsloth/llama.cpp/llama-server` (a symlink into
`~/.unsloth/llama.cpp/build/bin/`). It is the `unslothai/llama.cpp` fork tag
`b12588-mix-c0c3de8` (upstream base `b12588`, commit 883286076; updated by Unsloth Studio on 2026-11-21), built against the CUDA 13.3
toolkit.

- **Runtime deps:** only `libcudart.so.13`, `libcublas.so.13` and
  `libcublasLt.so.13`, all served by the system CUDA 13 in `/lib64`. So
  `backend.env.LD_LIBRARY_PATH` is `/lib64:/usr/lib64` and nothing else: no
  LM Studio vendor directory, no pip `nvidia-*` wheels, no NCCL.
- **NCCL is off** in this build. It only ever mattered for row-split
  all-reduce, and the GPU layout here is layer split, so nothing is lost.
- **SM coverage is 75-89 only** (RTX 3090 sm_86 and RTX 2060 sm_75 both fit).
  A Hopper or Blackwell card would need a different build.
- **The daily updater does not touch the production engine.**
  `llama-cpp-update.timer` (with `~/scripts/llama-cpp-update.sh`) is enabled
  and refreshes the *secondary* ai-dock CUDA 12.8 build in
  `~/sources/llama.cpp-cuda` (see [Secondary engine](#secondary-engine-llamacpp-cuda-and-perplexity-testing)).
  No backend runs it; it exists for offline tools such as `llama-perplexity`.
- **Unsloth Studio owns that directory.** Do not edit or replace files under
  `~/.unsloth/llama.cpp/`: Unsloth Studio manages them and may replace them
  on its own updates.
- **One model uses a patched build.** `inkling-2-mini` sets `binary:` to
  `~/sources/llama.cpp-inkling/src/build/bin/llama-server`: Unsloth's exact
  b12588 source (release asset `llama.cpp-source-commit-883286076...tar.gz`,
  checked against `llama-prebuilt-sha256.json`) plus a 33-line patch (`git diff`
  in that `src/`). Stock b12588 only uses Inkling 2's banded flash-attention
  kernel with f16/bf16 KV; with the q8_0 cache it builds a dense per-head bias
  that grows with context × ubatch and forces `-ub 128` at 262k. The patch lets
  the banded MMA kernel take q8_0/q5_0/q4_0 K/V (it already converts them to
  F16 per call), which allows `-ub 512` and about 2.7× faster prompt
  processing at long context; greedy output matches stock within run-to-run
  noise. To rebuild (for example on a newer Unsloth release), download that
  release's source asset, re-apply the diff, and build in the throwaway
  distrobox `llama-build` (`docker.io/nvidia/cuda:13.3.1-devel-ubuntu22.04`):
  `unset NVCC_CCBIN` first (the host profile sets `g++-15`, which the box lacks), then
  `cmake -B build -G Ninja -DCMAKE_BUILD_TYPE=Release -DGGML_CUDA=ON
  -DCMAKE_CUDA_ARCHITECTURES="75;86" -DGGML_CUDA_NCCL=OFF -DLLAMA_CURL=OFF
  -DLLAMA_OPENSSL=OFF -DLLAMA_BUILD_TESTS=OFF
  -DCMAKE_EXE_LINKER_FLAGS=-Wl,--allow-shlib-undefined && ninja -C build llama-server`
  (about 15 minutes; the linker flag is needed because the box has no
  `libcuda.so.1`). Unsloth Studio's updates do not touch this build.
- **The CLI is flag-compatible** with the ai-dock build it replaced (the
  `--help` output was byte identical at the time of the swap), so the flags in
  `config/config.yaml` carry over unchanged.

## Secondary engine: `llama.cpp-cuda` and perplexity testing

`~/sources/llama.cpp-cuda` (a symlink into `~/Nextcloud/Linux/Home/sources/`)
holds the **ai-dock CUDA 12.8 build** (`ai-dock/llama.cpp-cuda` releases,
asset `cuda-12.8-amd64.tar.gz`). It is **not** used to serve models. It is the
place for tools the Unsloth directory does not expose: `~/.unsloth/llama.cpp/`
only symlinks `llama-server` and `llama-quantize`, while this tree has
`llama-perplexity`, `llama-bench`, `llama-cli` and others. As of 2026-11-18: `v1.0.0`, build hash `2d8a3250`,
CUDA 12.8.1, archs 75/80/86/89/90/100/120 (`VERSION.txt` in that directory).

- **The updater replaces the whole directory.** `~/scripts/llama-cpp-update.sh`
  stages a new tarball and swaps it in, so anything you add inside
  `~/sources/llama.cpp-cuda` is lost on the next update. Keep scratch files,
  stubs and datasets elsewhere.
- **The launchers are tiny.** `llama-perplexity` and friends are about 14 KB
  and load `libllama-*-impl.so` from the same directory, so
  `LD_LIBRARY_PATH` must include that directory. The build's `RUNPATH` points
  at a CI path (`/workspace/llama.cpp/build/bin`) that does not exist here.
- **It does not start as-is.** `libggml-cuda.so` needs `libcudart.so.12`,
  `libcublas.so.12`, `libcublasLt.so.12` and `libnccl.so.2`; the system only
  has CUDA 13, and there is no NCCL anywhere. The workaround:
  - **CUDA 12 libs from LM Studio's vendor directory:**
    `~/.cache/lm-studio/extensions/backends/vendor/linux-llama-cuda12-vendor-v1/`
    (`libcudart.so.12`, `libcublas.so.12`, `libcublasLt.so.12`; the files date
    from 2025-02). Add it to `LD_LIBRARY_PATH`. This is read-only use of
    LM Studio's cache; do not modify it.
  - **Empty NCCL stub:** NCCL is only called for multi-GPU all-reduce, so an
    empty library named `libnccl.so.2` is enough to satisfy the loader (the
    8 undefined NCCL symbols are lazily bound and never called). Build it
    outside the tree:
    `echo 'void stub(void){}' | gcc -shared -fPIC -x c - -o libnccl.so.2 -Wl,-soname,libnccl.so.2`
    and put its directory on `LD_LIBRARY_PATH`. **Run on one GPU
    (`CUDA_VISIBLE_DEVICES=0`)**; do not use this build for multi-GPU tensor
    or row split, where the stub would be called and crash.
  - The production engine still needs none of this: `backend.env.LD_LIBRARY_PATH`
    stays `/lib64:/usr/lib64`.
- **Flash-attention pairs differ between builds.** The ai-dock build prints
  `FA_QUANTS = q4_0-q4_0,q8_0-q8_0,f16-f16,bf16-bf16,f8_e4m3-f8_e4m3` in its
  `system_info` line, so mixed K/V types are not among its compiled kernels.
  A `q8_0` K with `q5_0` V run still completed on it at a speed in line with
  `q8_0`/`q8_0` (about 12.7 s versus 14.0 s per 8192-token pass), so there was
  no sign of a slow CPU fallback, but that says nothing about the Unsloth
  engine. Confirm a mixed K/V pair on the engine that serves (load the model
  through llama-switch and check it generates at normal speed), not only here.
  **Confirmed on the Unsloth engine (2026-11-18):** `qwen-27b` with K `q8_0`
  and V `q5_0` loaded and served normally through llama-switch: 53.7 t/s
  generation on a short prompt, and 39.0 t/s generation at a 99k-token prompt
  (525 t/s prompt processing), with DFlash drafting active. The speeds match the
  `q8_0` figures recorded in the config comments, but there was no same-session
  `q8_0` A/B on this engine.
- **Perplexity results (2026-11-18).** `qwen-27b` UD-Q4_K_M, wikitext-2 test,
  `-c 8192`, 36 chunks, K `q8_0` in every run, all on the ai-dock build:

  | V cache | PPL | vs `q8_0` V |
  |---|---|---|
  | `q8_0` | 6.5111 ± 0.0435 | baseline |
  | `q5_0` | 6.5140 ± 0.0435 | +0.0029 (+0.04%) |
  | `q4_0` | 6.5344 ± 0.0437 | +0.0233 (+0.36%) |

  The runs use the same text, so the differences are tighter than the ± shown,
  which is the error of the absolute estimate. Even so, treat `q5_0` as
  indistinguishable from `q8_0` at this context length. Long-context recall
  was not measured.

### Measuring perplexity

Use this to check what a KV cache type, quant or engine change costs in
quality. It needs a text corpus; none is kept on the machine.

1. **Corpus (wikitext-2 test split, about 1.3 MB).** Download
   `https://huggingface.co/datasets/ggml-org/ci/resolve/main/wikitext-2-raw-v1.zip`
   (4.7 MB) into its own new empty directory and unzip it; the file you want is
   `wikitext-2-raw/wiki.test.raw`. Treat it as untrusted data: do not run
   anything from that directory. `~/.unsloth/llama.cpp/scripts/get-wikitext-2.sh`
   does the same job. The 2026-11-18 run used `/var/tmp/ppl-work/data/`, which
   is not persistent.
2. **Free the GPU first.** Unload the loaded model with
   `curl -X POST http://<server.host>:8080/models/unload -d '{"model":"<id>"}'`
   (`-H 'Content-Type: application/json'`). A 27B Q4_K_M model plus the
   desktop (about 1.2 GB on the 3090 with nothing loaded) fits on the 3090
   alone.
3. **Run it** (one run per setting, same model, same corpus):

   ```bash
   S=~/sources/llama.cpp-cuda
   V=~/.cache/lm-studio/extensions/backends/vendor/linux-llama-cuda12-vendor-v1
   LD_LIBRARY_PATH=$S:$V:<dir with libnccl.so.2 stub> CUDA_VISIBLE_DEVICES=0 \
     $S/llama-perplexity -m <model.gguf> -f <corpus>/wiki.test.raw \
     -ngl 99 -fa on -c 8192 -b 2048 -ub 512 -ctk q8_0 -ctv q5_0
   ```

   `-c 8192` gives 36 chunks and takes about 8 minutes per run on the 3090.
   Vary only `-ctk`/`-ctv` between runs so the numbers are comparable.
4. **Reading the result.** The tool prints `Final estimate: PPL = X +/- E`.
   Compare runs on the same corpus and context; differences smaller than
   about `E` are noise. Short Wikipedia articles do not exercise very long
   context, so this does not test recall at 250k+ tokens; use a
   long-context recall test for that.
5. **Do not compare across corpora.** The PPL values quoted in the
   `config/config.yaml` comments (for example 3.523 vs 3.531 for UD-Q4_K_XL)
   come from a different corpus; wikitext-2 gives roughly 6 on the same
   model. Record new results next to the setting they measure.
   `tools/ctxtest/ppl.sh MODEL CORPUS [-ctv q8_0 ...]` wraps step 3 and
   builds the NCCL stub in `tools/ctxtest/work/`.
6. **Reload after the test.** llama-switch loads nothing at startup; the next
   request loads the model again.

## Testing a new model or layout (`tools/ctxtest/`)

Before adding or re-tuning a model, measure it with the harness in
`tools/ctxtest/` (details in its `README.md`). Stop llama-switch first, run
`setup.sh` once, then:

- `launch.py <model-id> [--drop flag,flag] [-- flags...]` starts a test
  llama-server on `127.0.0.1:8300` with the same arguments llama-switch would
  build, plus your overrides. `--print` shows the command.
- `bench.py` for short-prompt speed and draft acceptance; `needle.py --fill 0.95 --image`
  for the worst-case VRAM low point (hold GPU0 at >= 600 MiB free, aim for 1 GB)
  and 10/50/90% recall; `ocr.py` for Hindi OCR accuracy; `quiz.py` for an
  Indian-law / Hindi-deed spot check with an answer key; `ppl.sh` for
  perplexity on the ai-dock build.
- `suite.py <model-id>` runs the standard set from `suite.yaml`. Every test
  saves a JSON result under `tools/ctxtest/results/` (the format is in the
  harness README). Grade quiz results with `grade.py` and rebuild
  `results/SUMMARY.md` with `report.py`. `results/` is gitignored because the
  repository is public, but it is the permanent record: never write results
  to `/tmp` or `work/` and never clear `results/` (the earlier quiz results
  lived in `/tmp` or `work/` and are gone).

Restart llama-switch afterwards, and re-run `./bin/llama-switch profile` for
any model whose config changed.

## Configuration reference (`config/config.yaml`)

- `server`: `host`, `port`, `backend_port_start/end`, `max_models`, `idle_timeout_minutes`, `health_timeout_seconds`, `sweep_interval_seconds`, `stream_prompt_progress` (default true; see [Prompt-progress keepalive](#prompt-progress-keepalive)).
- `backend`: `binary` (path to `llama-server`), `env` (notably `LD_LIBRARY_PATH` for CUDA libs), `common_args` (flags prepended to every model invocation), `workdir`, `nvidia_smi`, `ctx_checkpoints` (global default for `--ctx-checkpoints`), `cache_ram` (global default for `--cache-ram`, in MiB).
- `models`: list of `ModelConfig`. Lookup by `id` or `name` (`FindModel` matches `id` exactly, `name` case-insensitively). Each builds its llama-server args via `ModelConfig.BuildArgs`. Supports `mmproj` (multimodal), `tensor_split`, `ctx_checkpoints`, `cache_ram`, and freeform `extra_args`. A flag set in a model's `extra_args` replaces the same flag (and its values) from `backend.common_args` rather than being passed twice (`dropOverriddenArgs`; the VRAM-cache snapshot still records the two lists separately). Optional per-model override fields (`binary`, `args`, `health_path`, `env`) allow running non-llama-server backends — see [Per-model runtime override](#per-model-runtime-override). Both model lists (`/v1/models`, `/models`) emit `input_modalities` via `ModelConfig.InputModalities()`: `["text","image"]` when `mmproj` is set, else `["text"]`; the optional `vision` bool overrides this (needed for raw-`args` models, whose projector llama-switch can't see). Clients such as sai-portal sync vision capability from it.
- Path expansion: `~`, `~/...`, and `$VAR` are expanded in config values (`expand()`), including colon-separated `LD_LIBRARY_PATH`-style lists.

**Defaults applied when fields are zero/empty:** `backend_port_start=8201`, `backend_port_end=8299`, `max_models=2`, `idle_timeout_minutes=60`, `health_timeout_seconds=180`, `sweep_interval_seconds=15`, `queue_max_depth=64`, `queue_timeout_seconds=600`, `profile_drain_seconds=60`, `shutdown_drain_seconds=120`, `nvidia_smi="nvidia-smi"`. Validation rejects `server.port` overlapping the backend port range.

## Commands

```
./bin/llama-switch serve [config]    # start proxy (default if no command given)
./bin/llama-switch profile [config]  # load each model once, measure VRAM, save to config/vram-cache.json
./bin/llama-switch models [config]   # list configured models + VRAM estimates
./bin/llama-switch status [config]   # query a running server's /v1/loaded
./bin/llama-switch help
```

Config path resolution: positional arg → `$LLAMA_SWITCH_CONFIG` → `config.yaml` next to the binary (`./` and `../config/` relative to it) → `~/.config/llama-switch/config.yaml` → `./config/config.yaml`.

## Build & run

```bash
go build -o bin/llama-switch ./src   # produces ./bin/llama-switch
go vet ./...                         # static checks
go run ./src serve                   # run without explicit build
```

## Conventions

- **Single package in `src/`.** All Go code is `package main` in `src/`. Do not introduce subpackages without reason; the project's style is one file per concern. Config files live in `config/`, the built binary in `bin/`.
- **Go 1.26** toolchain; only stdlib + `yaml.v3`. Avoid adding dependencies for things the stdlib can do.
- **Comment style:** section dividers use `// ── Name ──────` banners; exported functions carry doc comments; `Caller must hold <mu>` notes annotate lock contracts — respect these when editing.
- **Locking:** `BackendManager.mu` guards the `backends` map and port allocator interactions during lifecycle. Methods suffixed `Locked` require the caller to hold the lock (e.g. `startBackendLocked`, `stopLocked`, `ensureCapacityLocked`, `evictLRULocked`). Preserve the double-checked-locking pattern in `EnsureLoaded` (RLock fast path → Lock slow path).
- **Process output** from each backend is piped through `logPipe` and printed to stdout with a `[model-id]` prefix — keep this; it's how service logs are read.
- **Unload reasons are logged.** Every unload goes through `stopLocked(id, b, reason)`, which logs `[model-id] unloading: <reason>` (idle timeout, LRU eviction for `max_models` or VRAM with the model being admitted and free VRAM per GPU, `/models/unload` with the client address, profiling, health-check failure, shutdown). `evictLRULocked` and `StopModel` take a reason too; pass a specific one when adding a new unload path.
- **Streaming detection** in `forward()` keys off the backend response's `Content-Type`: SSE responses (`text/event-stream`) are forwarded event-by-event via `streamSSE` (flush after each `\n\n`-delimited event); all other responses use a plain `io.Copy`. `streamSSE` takes an optional `*progressRewriter` (nil = byte-for-byte passthrough).
- **Errors during backend start** (port alloc fail, binary missing, health timeout) must release the port and clean up — mirror the cleanup in `startBackendLocked`.
- **Config is authoritative.** `config/config.yaml` reflects a real deployment with specific GGUF paths, GPU topology, and a bind address. Treat it as live configuration, not an example template.
- **Tests exist** in `src/` (per-model runtime override in `llama_switch_test.go`, Chandra OCR handler in `chandra_handler_test.go`, plus `http_proxy_test.go`, `inflight_test.go`, `findmodel_vram_test.go`). Run `go test ./...` to execute all tests; use `-short` to skip integration tests.

## Common tasks for agents

- **Add a new model:** add an entry under `models:` in `config/config.yaml`; run `./bin/llama-switch profile` so admission control has VRAM estimates. Set `cache_ram: 0` on models with no prefix reuse (OCR, one-shot) to avoid wasting system RAM on the host-memory prompt cache.
- **Add a non-llama-server model:** set `binary`, `args` (with `{port}`), and optionally `health_path`/`env` on the model config. The rest of llama-switch handles it automatically.
- **Add a new HTTP endpoint:** add a path branch in `ProxyServer.handle` (`src/proxy.go`) and a `handleXxx` method. Management/model-list endpoints return JSON; proxying goes through `handleProxy` → `forward`.
- **Add a model handler:** implement the `ModelHandler` interface in a new `*_handler.go` file under `src/`, register it in `NewModelHandler()` (currently in `src/chandra_handler.go`). The handler intercepts responses in `forwardWithHandler`.
- **Remove a model handler:** delete its `*_handler.go` and `*_handler_test.go` files from `src/`, remove the registration line in `NewModelHandler()`. The generic infrastructure in `src/proxy.go` can stay.
- **Change eviction policy:** `ensureCapacityLocked` and `evictLRULocked` in `src/backend.go`. LRU is based on `Backend.lastReq`, updated via `Touch()` on every proxied request.
- **Change CLI surface:** `src/main.go` `switch cmd` block + `usageText`. `parseConfigArg` handles config-path discovery.
- **Rebuild after edits:** `go build -o bin/llama-switch ./src` (replaces `bin/llama-switch`); restart the systemd unit if running as a service.
- **After an engine change:** `config.yaml` is read only at startup, so restart the `llama-switch` unit to apply a new `backend.binary` or `backend.env`. Then re-measure VRAM with `./bin/llama-switch profile --force` (the plain `profile` command reuses cached measurements from `config/vram-cache.json`, which are engine specific).

## Things to watch out for

- `ReadTimeout`/`WriteTimeout` on the proxy server are intentionally `0` to allow long-lived streaming requests — do not set finite timeouts without accounting for streaming.
- The VRAM headroom constant is `1024` MB (1 GB) in `ensureCapacityLocked` (`src/backend.go`). It is applied **only to the primary GPU** (CUDA0 / index 0) to account for OS/display-server overhead; secondary GPUs have no display output and thus no headroom. Adjust there if changing the safety margin.
- Per-GPU admission control (`vramFitsPerGPU` in `src/vram.go`) checks each GPU the model targets individually. If per-GPU profile data is unavailable (legacy cache entries without `gpu_vram`), it falls back to the aggregate VRAM check. Keep this fallback intact.
- VRAM measurements are validated during profiling (`validateVRAMMeasurement` in `src/vram.go`): rejected if below 256 MB or below the model's `.gguf` file size. Both the `profile` command and auto-profiling during `serve` enforce this. Rejected measurements are not cached.
- `waitHealth` polls every 2 s; large models may take close to `health_timeout_seconds` (default 180 s) to become ready. The proxy returns `503` with `Retry-After: 30` if a model fails to load.
- `nvidia-smi` is required for VRAM-aware scheduling; if it is unavailable, `ensureCapacityLocked` falls through optimistically (loads without VRAM checks) — keep this fallback intact.
- `config/config.yaml` contains absolute paths specific to the deployment machine; don't generalize them.
- In-flight request tracking: each `Backend` has an atomic `inFlight` counter, incremented in `handleProxy` before forwarding and decremented via `defer`. Eviction (`evictLRULocked`), idle sweeping (`sweepIdle`), and explicit unload (`StopModel`) all skip backends with `InFlight() > 0` to avoid killing active requests.
- Capacity queue: when `EnsureLoaded` can't evict (all backends in-flight), the caller releases the write lock and blocks on a channel (`capCh`) until a request completes and calls `SignalCapacity()`, or until the queue timeout (default 600s / 10 min). Requests for already-loaded models hit the fast path and never wait. Max queue depth is `queue_max_depth` (default 64); beyond that, new requests get an error. The queue is best-effort FIFO (goroutine scheduling order, not guaranteed).
- Drain mode: `BackendManager.StartDraining()` sets an atomic flag that causes `EnsureLoaded` and `handleProxy` to return 503. Used during remote profiling and shutdown: the signal handler calls `StartDraining()` then `WaitIdle(shutdown_drain_seconds)` before `Stop()`, so active requests complete before backends are killed. `WaitIdle(timeout)` blocks until all in-flight counters reach zero.
- Remote profiling: `POST /admin/profile` (or `?force=true`) triggers profiling on the running service. The CLI `profile` command auto-detects a running service and delegates to this endpoint, streaming SSE output to stdout. Concurrent profiling requests are rejected.
- The `loading` map (in `EnsureLoaded`) only de-duplicates concurrent requests for the *same* model; it is registered before the capacity wait loop and does **not** reserve resources. Resource reservation lives in `BackendManager.reserved`, which `ensureCapacityLocked` sets only when a model starts evicting on its own behalf or is admitted, and clears on error return or in `deleteLoading`. Only `reserved` models count toward `MaxModels` and pending VRAM. Do not count `loading` entries as pending: two different models queued behind a busy backend would each treat the other as about to consume VRAM, both report "waiting for 1 loading model(s)" after the busy backend is evicted, and the GPU sits empty until `queue_timeout_seconds` (regression test: `TestCapacityQueueTwoWaitersDoNotDeadlock`).
- `ensureCapacityLocked` counts `len(backends) + (other reserved models not yet running) + 1` against `MaxModels`; the `+1` is the model being admitted.
- Host-memory prompt cache (`--cache-ram`): llama-server b10142+ defaults to 8192 MiB of system RAM for a prompt cache that stores KV states of completed requests for prefix reuse. This is separate from VRAM and from `--ctx-checkpoints`. The `cache_ram` config field (backend-level global, per-model override) controls this. Set `cache_ram: 0` on models with no prefix reuse (OCR, one-shot models). The model-level field uses `*int` so that explicit `0` (disable) is distinguishable from unset (inherit backend default).
